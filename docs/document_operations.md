# 자료 처리·운영 가이드

## 현재 흐름

메모 생성·수정은 문서와 색인 작업을 같은 DB 트랜잭션에 저장합니다. HTTP 요청은 작업 접수 후 반환하고 백그라운드 작업자가 RAG를 호출합니다. PDF는 서명 URL로 업로드한 뒤 complete에서 Storage HEAD로 실제 파일·크기를 검증합니다. 검증된 파일의 완료 상태는 색인 접수가 실패하더라도 보존합니다.

작업은 `document_jobs`에 남습니다. 작업자는 `FOR UPDATE SKIP LOCKED`로 하나를 획득하고 10분 lease와 고유 token을 받습니다. 종료된 서버의 작업은 lease 만료 후 다른 작업자가 이어받습니다. 예전 작업자의 완료 기록은 token 조건으로 거절합니다. 문서 버전이 바뀌거나 삭제되면 이전 작업은 종료하고 새 문서를 건드리지 않습니다.

같은 문서·버전의 접수는 중복 차감하지 않습니다. 이미 ready인 버전은 재색인하지 않습니다. RAG도 문서별 transaction advisory lock을 잡아 HTTP 시간 초과 후의 재요청이 동시에 임베딩하지 못하게 합니다.

## 한도와 알림

| 설정                          | 기본값    | 의미                                        |
| ----------------------------- | --------- | ------------------------------------------- |
| `DOCUMENT_MAX_COUNT`          | 100       | 모임당 자료 개수. 삭제 정리 중인 PDF도 포함 |
| `DOCUMENT_MAX_BYTES`          | 209715200 | 모임당 200MiB 할당 용량                     |
| `DOCUMENT_DAILY_UPLOAD_LIMIT` | 20        | 사용자별 하루 신규 PDF 업로드 접수          |
| `DOCUMENT_DAILY_INDEX_LIMIT`  | 20        | 사용자별 하루 색인 작업 접수                |
| `MAX_CHUNKS` (RAG)            | 200       | 문서당 청크 최대 개수                       |
| `DB_POOL_SIZE`                | 5         | Spring DB 연결 풀 상한                      |

PDF는 선언한 크기로 한도를 우회하지 못하도록 파일당 최대 20MiB를 확보합니다. 메모는 UTF-8 본문 크기로 계산합니다. 파일 삭제가 완료되어야 할당 용량이 돌아오므로 삭제 직후에는 정리 대기 용량이 포함됩니다. 업로드 완료 시 파일의 실제 크기를 다시 기록합니다.

일일 한도는 한국 시간 자정에 초기화합니다. 질문의 사용자별 통합 30회와 자료 업로드·색인 접수 한도는 별도입니다. 색인 접수에 대한 자동 재시도는 추가 접수로 세지 않으며, 최대 5번으로 제한합니다. 같은 버전의 정상 완료 이후 재요청은 무료입니다. 80% 이상 사용하거나 한도에 도달하면 사용자 내용·토큰을 포함하지 않는 WARN 로그를 남깁니다.

이 로그는 실제 달러 사용액 알림이 아닙니다. OpenAI 계정의 예산·과금 알림은 운영 계정에서 별도로 관리해야 합니다. 제한 수치는 환경변수로 조정할 수 있습니다.

## 실패·재시도

네트워크·상위 서비스의 일시적 오류는 30초부터 지수적으로 간격을 늘려 최대 5번 재시도합니다. 손상된 PDF, 텍스트 없는 스캔 PDF, 크기·페이지·분량 제한 초과는 자동 반복하지 않고 오류를 표시합니다. 상위 인증 실패도 설정 확인이 필요하므로 종료합니다. 자동 재시도가 끝나면 `INDEX_RETRY_EXHAUSTED`를 표시하고 사용자가 다시 접수할 수 있습니다.

브라우저는 서버가 `processing_active=true`로 알려주는 pending/processing 자료만 5초 간격으로 갱신합니다. 화면을 벗어나거나 숨겨지면 요청을 멈추고, ready/failed 또는 접수되지 않은 작업에서는 반복 조회하지 않습니다. 저장 성공 안내와 AI 반영 완료 안내를 구분합니다.

업로드 실패는 같은 문서의 `/upload-url`에서 새 URL을 받아 이어서 진행합니다. 업로드가 실제로 끝났는데 색인 한도·연결 오류가 나면 파일을 다시 만들지 않고 자료 상세에서 AI 반영을 재시도합니다. 기존 파일이 없다는 것을 확인한 자료도 업로드 재개 상태로 전환할 수 있습니다.

## 삭제와 미완료 자료 정리

자료·모임 삭제는 파일 삭제 작업 등록과 DB 삭제를 함께 커밋합니다. 외부 Storage 호출을 DB 삭제 앞에 두지 않습니다. 생성·수정·업로드 재개·삭제는 모임→문서 순서의 잠금을 사용해 동시 요청에서 파일 목록과 최신 서명 URL 만료 시각을 보존합니다.

파일 삭제는 마지막 업로드 URL의 만료 시각 이후 5분을 더 기다립니다. 오래된 URL로 파일을 다시 쓰는 상황을 줄이기 위한 지연이며, 삭제된 자료는 즉시 목록과 새 다운로드 권한에서 제외됩니다. Storage 장애 시 삭제는 횟수 제한 없이 간격을 늘려 재시도합니다.

미완료 업로드는 2시간 유효기간 이후 주기적으로 DB에서 제거하고 파일 삭제를 예약합니다. 기존 데이터의 `upload_completed`는 true로 보존했으므로 과거 자료를 일괄 삭제하지 않습니다. Storage에서 24시간 이상 지난, 문서에 연결되지 않은 규격 경로는 별도로 탐지하고 3시간 뒤 삭제를 예약합니다. 비규격 경로나 다른 버킷은 건드리지 않습니다.

## 적용과 운영 확인

Supabase의 `durable_document_jobs` 마이그레이션은 **2026-10-13 적용 완료**입니다. 이 프로젝트에서 같은 SQL을 다시 실행하지 않습니다. 파일은 [20261013060107_durable_document_jobs.sql](../supabase/migrations/20261013060107_durable_document_jobs.sql)이며 Flyway 복사본은 V4입니다. 현재 `FLYWAY_ENABLED=false`를 유지합니다. 별도 DB에 설치할 때만 해당 DB의 마이그레이션 이력에 맞게 적용합니다.

배포 순서는 DB → Python RAG → Spring → 프론트엔드입니다. 새로운 프론트는 메모 색인을 서버에 맡기므로 이전 Spring만 실행 중이면 자동 반영이 작동하지 않습니다.

Spring은 `PORT`를 사용하며 기본은 8080입니다. `DOCUMENT_JOBS_ENABLED=true`가 기본입니다. `/healthz`는 프로세스 생존 상태, `/readyz`는 DB와 필수 작업·질문 한도 테이블 준비 상태를 반환합니다. 인증정보나 DB 상세는 응답에 포함하지 않습니다. Render의 backend health check에는 `/readyz`를 사용하고 RAG 연결은 별도로 점검합니다.

```sh
HEALTH_BACKEND_URL=https://moadam.onrender.com node scripts/check-service-health.mjs
RAG_URL=https://YOUR_RAG_SERVICE.onrender.com node --env-file=.env scripts/check-ai-deployment.mjs
```

무료 서비스의 유휴 정지는 정기 작업의 실행도 지연시킬 수 있습니다. 정리·색인이 항상 제시간에 실행되어야 하는 운영 환경에서는 실행이 유지되는 backend 서비스를 사용해야 합니다. 유휴 후 깨어나더라도 DB 작업 기록은 유지하고 lease 만료 작업을 복구합니다. [Render 무료 서비스 안내](https://render.com/docs/free).

현재 운영 backend의 공개 API 문서는 90초 요청에서도 시간 초과했습니다. Render 관리 로그·설정에 접근하지 못해 장애 원인과 운영 복구 완료 여부는 확정하지 못했습니다. backend의 기동·배포 로그, 실제 DB 환경변수, 서비스 플랜과 RAG 주소·토큰 설정을 확인해야 합니다.

## 검증 명령

격리 검증은 `mvn verify`, `pnpm test:db`, RAG unittest, 프론트 `pnpm check`, `pnpm build`, `pnpm test:documents-ui`입니다. 문서 UI 검증은 `make qa`에도 포함합니다.

실제 연동 검증은 명시적으로 실행하는 다음 명령입니다. 임시 Auth 사용자·모임·파일을 만들고 제거하며 작은 임베딩·모델 요청을 사용하므로 기본 QA에서는 실행하지 않습니다.

```sh
node --env-file=.env scripts/document-jobs-live-smoke.mjs
```
