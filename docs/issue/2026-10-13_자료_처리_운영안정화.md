# 자료 자동 색인·비용 제한·업로드/삭제 복구와 운영 연결 점검

- 작성일: 2026-10-13 (한국 시간)
- 상태: 자료 처리 코드·DB 적용·실제 로컬 연동 검증 완료 / 운영 배포·backend 장애 확인 대기
- 영향 범위: 자료 저장·수정·업로드·색인·삭제, 상태 UI, DB 작업 큐, 상태 확인 API

## 어떤 이슈였나

[초기 점검](../service_release_review_2026-10-13.md)에서 운영 backend 시간 초과, 메모 수정 후 색인 누락, 색인 실패의 성공 안내, 자료 총량·비용 제한 부재, 업로드·삭제 불일치, 긴 동기 색인 문제를 확인했습니다. 사용자 요청에 따라 코드를 수정하고 실제 연동을 검증했습니다.

## 원인과 해결

| 문제                         | 원인                                          | 수정                                                                                             |
| ---------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 수정 메모가 AI 검색에서 빠짐 | pending 전환 후 재색인 호출 없음              | 생성·수정과 DB 작업 접수를 같은 트랜잭션에 저장, 서버에서 자동 처리                              |
| 실패를 성공으로 안내         | RAG의 failed 결과를 저장 성공과 구분하지 않음 | 영구 오류·재시도·재시도 소진을 구분하고 UI에 실제 상태 표시                                      |
| 저장 공간·색인 비용 증가     | 누적 한도와 반복 처리 방지 없음               | 모임 100개·200MiB 할당, 사용자 하루 업로드 20·색인 접수 20, 동일 버전 중복 방지, 80% 사용량 로그 |
| 업로드 중단·미완료 자료      | 새 행 생성 후 실패 시 재사용·정리 없음        | 같은 행에 URL 재발급, 실제 파일 HEAD 검증, 완료 파일 보존, 만료 업로드 정리                      |
| 삭제 중 DB/파일 불일치       | 외부 삭제를 DB 커밋 전에 실행                 | DB outbox 등록 후 비동기 삭제, 최신 URL 만료 보존, 장애 재시도 및 보수적 고아 파일 탐지          |
| 긴 색인 HTTP 시간 초과       | 브라우저 요청 안에서 전체 색인 실행           | durable 작업 큐·worker, lease 복구·token fencing, RAG 문서 잠금                                  |
| 운영 backend 응답 없음       | 관리 로그를 확인하지 못해 원인 미확정         | 생존/준비 API·진단 스크립트·5초 DB 획득 제한·PORT 대응을 추가. 운영 복구는 미확인                |

실제 PDF 검증 중 추가로 드러난 문제도 수정했습니다. 손상 PDF 파서 예외가 일반 실패로 분류돼 반복되던 부분을 `INVALID_PDF`로 처리했습니다. 삭제 시 `Instant`를 JDBC에 그대로 전달해 500이 발생하던 부분은 SQL timestamp로 변환하고 회귀 테스트를 추가했습니다. 업로드 재개 후 실제 크기와 최신 URL 만료 시각을 보존하며, 모임·문서 잠금 순서를 통일했습니다.

처리 중인 작업만 UI에서 조회하도록 `processing_active`를 추가해 한도 초과·수동 재처리가 필요한 자료가 계속 polling되지 않도록 했습니다. 자세한 정책과 관련 파일은 [운영 가이드](../document_operations.md)에 있습니다.

## 검증 결과

- backend Maven: 49개 테스트 통과. 작업 중복·접수 한도·용량·영구 실패·삭제 재시도·JDBC 날짜 바인딩·상태 확인을 검증했습니다.
- RAG: 21개 unittest와 Ruff 통과. 동일 버전 ready 재사용, 동시 색인 거절, 미완료 업로드 차단, 손상 PDF 분류를 포함합니다.
- 격리 PostgreSQL(PGlite): 신규 마이그레이션, lease 재획득, 이전 token 완료 거절, RLS 접근 차단, 보수적 고아 파일 등록·중복 방지 통과.
- 프론트 검사·빌드, 1440px·390px 문서 UI 검증 통과. 자동 상태 갱신, 중복 행 없이 업로드 재개, OCR 실패 안내, 질문 버튼 제한을 확인했습니다.
- 기존 성능·모아AI 에러 UI QA 통과.
- 실제 로컬 Spring/RAG + Supabase/OpenAI: 메모 생성·수정 자동 색인, 새 버전의 토요일 회의를 근거로 한 grounded AI 답변, 같은 버전 재요청 시 추가 차감 없음 확인.
- 실제 Storage: URL 재발급 후 업로드, HEAD 검증, 빈 PDF의 OCR 안내, DB 삭제 작업의 파일 삭제 완료 확인.
- 임시 업로드 만료를 시험용 행에서 앞당겨 정기 작업이 자료를 제거하는 것을 확인했습니다. 임시 사용자·모임·파일을 정리했습니다.
- 실제 `/healthz`, `/readyz` 모두 HTTP 200 확인. 이는 로컬 결과이며 Render 운영 복구를 뜻하지 않습니다.

## 실제 적용 상태

Supabase 연결 프로젝트에 `durable_document_jobs`를 migration version `20261013060107`로 적용했습니다. 새 테이블은 RLS를 활성화하고 anon/authenticated 직접 접근을 차단했습니다. 기존 데이터는 유지했습니다. [Supabase search_path 안내](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable)에 따라 `touch_updated_at`의 search_path 경고도 보완했으며 advisor에서 해당 경고가 사라짐을 확인했습니다. RLS 정책 없음 안내는 서버 전용 테이블의 의도된 접근 차단입니다.

로컬 backend와 RAG를 최신 코드로 실행했습니다. 개발 중 빌드 파일 변경이 실행 중 jar에 영향을 주지 않도록 별도 실행 사본을 사용했습니다. Render·Vercel 배포는 수행하지 않았습니다.

## 남은 운영 확인

- Render 공개 API 요청은 90초에도 응답이 없었습니다. 기동·오류 로그와 서비스 설정이 필요하며, 무료 플랜 때문이라고 확정하지 않았습니다.
- 신규 코드를 RAG → backend → frontend 순서로 배포하고 `/readyz`, RAG 준비 상태, 로그인 후 전체 자료 흐름을 확인해야 합니다.
- 정기 작업의 제시간 실행을 요구하면 유휴 정지되는 backend 환경을 피해야 합니다. 플랜 변경은 수행하지 않았습니다.
- OpenAI 계정의 실제 달러 예산·과금 알림 설정은 계정에서 별도 확인해야 합니다. 앱의 사용량 제한·로그는 실제 과금 알림과 구분합니다.

기존 [운영 모아AI 연결 이슈](2026-10-13_배포환경_모아AI_응답실패.md)는 운영 확인 대기 상태를 유지합니다.

## 2026-10-13 마이그레이션 재실행 오류 후속

사용자가 SQL Editor에서 기존 SQL을 실행할 때 `42701: column "upload_completed" of relation "documents" already exists` 오류를 보고했습니다. 이 오류는 컬럼이 이미 존재한다는 의미이며, 위 실제 적용 기록과도 일치합니다. 나머지 스키마의 현재 운영 상태는 이번 작업에서 직접 조회하지 않았습니다.

사용자의 기존 마이그레이션 파일 수정 요청에 따라 Supabase SQL과 Flyway V4 복사본의 두 컬럼·두 테이블·세 인덱스 생성문에 `IF NOT EXISTS`를 추가했습니다. RLS 활성화·권한 회수·함수 search_path 설정은 유지했습니다. 이름이 같은 기존 객체의 정의를 자동으로 보정하지는 않습니다. 이미 적용된 Flyway V4는 파일 수정으로 체크섬이 달라질 수 있으므로, 해당 환경이 있다면 재기동 전 적용 이력을 확인해야 합니다.

마이그레이션 복사본 검사와 `pnpm test:db`, `make conventions`를 통과했습니다. 추가 격리 PGlite 검사에서 `upload_completed`가 이미 있는 상태로 실행한 뒤 전체 SQL을 다시 실행해도 통과하며, 작업 행 보존·세 인덱스·RLS·클라이언트 접근 차단을 확인했습니다. 운영 DB 쓰기 및 배포는 수행하지 않았고, 상태는 파일 수정 완료 / 운영 재실행 확인 대기입니다.
