# 모아AI 토큰 사용량 및 일반 답변 개선

- 최초 수정 기록: 2026-10-13 (한국 시간)
- 검증 완료: 2026-10-14 (한국 시간)
- 상태: 코드 수정 완료 / 운영 migration·배포 확인 대기
- 영향 범위: DB 사용량 원장, Spring 한도 API, RAG 일반/자료 답변, 모아AI 화면

## 어떤 이슈였나

사용자별 하루 30회 제한은 질문의 길이·대화 내역·자료 발췌·답변 길이가 달라도 같은 1회로 차감했다. 실제 토큰 사용량만큼 하루 사용량을 %로 표시하도록 변경하고, 일반 질문도 마크다운으로 읽기 좋게 답변하며 여러 질문으로 핵심 강조와 줄바꿈을 확인해 달라는 요청이었다.

## 구현 내용

- 하루 기본 120,000토큰을 100%로 둔다. 이는 평균 4,000토큰 × 약 30회라는 초기 가정이며 실제 질문 수를 고정하지 않는다. `AI_DAILY_TOKEN_BUDGET`으로 조정한다. 기준 날짜와 초기화는 Asia/Seoul 자정이다.
- `ai_daily_token_usage`와 `ai_token_requests`를 새 V5/Flyway 및 대응 Supabase migration에 정의했다. 기존 30회 기록은 보존하지만 새 한도에 사용하지 않는다. 과거 실제 토큰 수를 알 수 없으므로 임의로 실제 사용량으로 환산하지 않는다.
- Spring이 남은 잔액 안에서 요청별 최대 20,000토큰을 원자적으로 예약한다. RAG가 단 한 번 해당 예약을 시작하도록 조건부 UPDATE로 claim한다. 중복 전달이 두 번의 모델 생성으로 이어지지 않는다.
- 모델 입력·출력·자료·대화 내역과 검색 임베딩·검색 질문 보완의 실제 `usage.total_tokens`를 합산한다. 입력/출력의 단가 차이를 적용한 달러 예산 방식은 아니다. cached input도 토큰 수 기준으로 포함한다.
- 누적 토큰 정산으로 같은 완료/정산을 다시 처리해도 중복 차감하지 않는다. 입력·출력 상한은 tiktoken으로 사전 확인하며 실제 provider 사용량을 우선한다. 최소 출력 여유가 없으면 추가 모델 호출 없이 안내한다.
- 스트리밍은 `include_usage=true`로 마지막 실제 usage를 받는다. length/content_filter 종료도 마지막 usage까지 읽어 정확히 정산한 뒤 오류로 처리한다. 요청을 보내기 전 취소·명확한 연결 실패·HTTP 거부는 생성 입력 토큰을 차감하지 않는다.
- 중단이나 읽기 시간 초과로 최종 usage를 받지 못하면 입력과 받은 출력 토큰을 추정해 `estimated=true`로 저장한다. 강제 프로세스 종료·영구 DB 장애·provider가 보내지 않은 출력까지 정확하게 복원하는 기능은 아니다.
- 실패 시 백엔드는 아직 RAG가 시작하지 않은 예약만 해제한다. 시작된 요청은 RAG가 정산 후 해제하므로 시간 초과/브라우저 중지 후 진행 중인 작업의 예산을 조기에 풀지 않는다. 현재 날짜의 5분 만료 예약은 다음 예약 시 회수한다. 자정을 넘긴 완료는 요청을 시작한 날짜에 정산한다.
- 대화 저장·삭제·서버 재시작은 사용량을 초기화하지 않는다. 생성 동안 Spring의 대화 저장 트랜잭션을 유지하지 않고 완료 후 질문/답변을 한 번에 저장한다.
- API/생성 타입을 토큰 수·예약량·사용/잔여 퍼센트·초기화 시간으로 함께 갱신했다. 화면에는 “오늘 남은 사용량 75%”처럼 표시한다. 원장과 함수는 RLS 및 권한 회수로 브라우저 직접 접근을 차단했다.

## 일반 질문과 가독성

일반 설명·학습·코드·일반적인 조언은 모임 자료가 없어도 답한다. 모임 활동 추천 같은 조언과 실제 회비·일정 조회를 구분한다. 실제 내부 사실은 현재 문서 근거가 필요하며 일반 답변에 출처를 지어내거나 “자료에서 확인 필요” 배지를 붙이지 않는다. 일반 지식 답변도 같은 개인 세션의 후속 맥락으로 보관한다. 인터넷 검색 기능은 추가하지 않았다.

실제 모델 테스트에서 일반 설명이 한 문단에 뭉치는 경우와 활동 추천의 핵심 강조 누락을 발견했다. 생성 지침을 강화하고 최종 문장 사이를 문단으로 정리한다. 이미 있는 마크다운과 fenced/인라인 코드를 보호한다. 모델이 강조를 생략하면 짧은 목록 레이블·정의의 주제·정보 부족 안내의 핵심 구절을 제한적으로 굵게 처리하며 문장 전체를 임의로 강조하지 않는다. 서식 보완은 모델을 다시 호출하지 않는다.

작성 중에는 마크다운을 표시하고 최종 정리 내용이 다르면 기존 done 처리로 최종 답변을 반영한다. 실제 스트리밍의 한 줄 설명이 완료 후 여러 문단으로 교체되는 흐름도 화면에서 확인했다. 굵은 글씨 안의 인라인 코드도 코드 요소로 렌더링한다.

## 실제 모델 및 화면 검증

모델은 기존 `gpt-4.1-mini`를 유지했다. 질문은 합성 데이터이며 DB는 메모리 fixture로 대체했다. 실제 OpenAI 생성/임베딩/usage는 사용했지만 운영 DB와 회원 자료를 읽거나 쓰지 않았다. 초기 서식 실패를 수정하며 8종 질문을 반복 테스트했고, 모임 활동 추천과 실제 스트리밍도 추가 확인했다. 아래 표는 마지막 성공 결과이며 전체 시도에 사용한 토큰의 합계는 아니다.

| 일반 개념 설명      | 1,392 |           1 |         3 | 통과 |
| 단계별 안내         | 1,618 |           7 |         8 | 통과 |

- 9종 질문의 마지막 결과: 14,255토큰.
- 실제 스트리밍 1회: 1,385토큰. delta 수신·일반 답변·실제 provider usage 정산을 확인했다.
- 마지막 검증 묶음 합계: 15,640토큰. 이 짧은 합성 질문 평균을 실제 회원의 30회 평균으로 일반화하지 않는다.
- 한 문장짜리 짧은 후속 답변은 한 문단을 허용한다. 여러 문장의 일반 설명과 안내는 문단으로 나누며 목록은 항목별 새 줄을 유지한다.
- 모델의 실제 생성 답변을 1440px/390px 브라우저에 재생해 `<strong>`/font-weight, 문단·목록·코드블록, HTML 비실행, 가로 넘침 없음, 최종 서식 교체, 사용량 % 갱신을 확인했다. 모델 응답에 서버의 최종 서식 처리를 포함한 결과다.
- 원본 결과는 `/tmp/moadam-markdown-live-report.json`, 화면 캡처는 `/tmp/moadam-ai-error-qa/live-*.png`에 있다.

## 필수 검사

RAG Ruff 및 unittest, Spring `mvn verify`, 프론트 `pnpm check/build`, DB 격리 검사, AI 화면/스트리밍/성능/캐시 검사를 실행한다. 최종 검사 명령과 결과는 아래 완료 기록에 남긴다. 실제 운영 부하, 실회원 데이터와 원격 DB의 통합 동작까지 검증한 결과는 아니다.

## 운영 적용과 남은 작업

운영 DB migration과 배포는 수행하지 않았다. V5/Flyway 또는 대응 Supabase migration을 먼저 적용하고 백엔드·RAG·프론트 변경을 함께 배포해야 한다. 첫 전환 때 새 토큰 원장이 시작되며 기존 30회 기록은 그대로 남는다. 별도 서버 DB 역할을 쓴다면 필요한 테이블과 함수 권한만 서버 역할에 부여해야 한다. 실제 회원 사용량을 측정해 초기 하루 예산을 조정한다.

[OpenAI 스트리밍 사용량 문서](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)에 따라 중단 시 마지막 usage가 없을 수 있음을 반영했다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)에 따라 새 원장 테이블은 브라우저 역할의 직접 접근을 허용하지 않는다.

## 2026-10-14 연결 종료 후 후속 검증

이전 작업 기록과 변경 파일을 확인해 시간 초과 시 예약 해제 경로부터 점검했다. Spring 실패 경로는 `ai_finish_tokens(..., true)`로 아직 시작하지 않은 예약만 해제하며, 시작된 요청은 RAG 정산에 맡기는 코드와 회귀 검사가 남아 있었다.

전체 RAG 검사를 다시 실행했을 때 목록 레이블의 굵은 표시를 반영하지 못한 기존 기대값 2개가 실패했다. 최종 답변 기대값을 구체적인 마크다운 문자열로 수정했다. 스트리밍 중 원문 delta를 먼저 수신하는 검사는 그대로 유지했다.

- RAG: Ruff check/format 및 unittest **48개 통과**.
- Spring: Spotless 검사를 통과했고, 로컬 포트가 필요 없는 AI 사용량·스트리밍·자료 작업·권한 정책 등 단위 테스트 **37개 통과**. Mockito는 명시적 javaagent로 실행했다.
- 프론트: `pnpm check`(포맷·린트·타입), `pnpm exec next build --webpack`, `pnpm test:cache` 통과.
- DB: `pnpm test:db` 통과. PGlite에서 토큰 예약, 시작된 요청의 취소 시 예약 유지, 중복·늦은 정산, 사용자/날짜 분리, 만료 회수 및 브라우저 역할 접근 차단을 확인했다.
- 마크다운: 이전 실제 모델 결과 파일의 9종 답변과 스트리밍 답변을 현재 React 컴포넌트로 서버 렌더링해 `<strong>`, 문단/목록, 코드블록을 재확인했다. 굵은 표시 안의 인라인 코드와 HTML 이스케이프도 통과했다. 이번에는 실제 모델을 추가 호출하지 않았다.
- 저장소 구조·마이그레이션 복사본 검사 및 `git diff --check` 통과.

현재 실행 환경은 로컬 포트 바인딩을 `Operation not permitted`로 차단한다. 따라서 기본 Turbopack 빌드와 전체 `mvn verify`의 서버 기반 검사, `pnpm test:chat-stream`은 실행 환경 오류로 완료하지 못했다. Webpack 빌드는 성공했지만 전체 기본 검사 성공으로 표현하지 않는다. 브라우저 AI 화면·성능 QA도 이번에는 재실행하지 않았으며, 위의 기존 모바일/데스크톱 검증과 이번 서버 렌더링 검증을 구분한다.

운영 DB migration·서비스 배포는 여전히 수행하지 않았다. 백엔드 설정은 기본값이 있으므로 선택적으로 `AI_DAILY_TOKEN_BUDGET=120000`, `AI_REQUEST_TOKEN_BUDGET=20000`을 등록할 수 있다. 이 두 변수는 Spring 백엔드 설정이며 프론트/RAG에 추가할 변수는 아니다.
