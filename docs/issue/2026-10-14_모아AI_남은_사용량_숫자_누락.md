# 모아AI 남은 사용량 숫자 누락

- 작성일: 2026-10-14 (한국 시간)
- 상태: 로컬 전체 재시작 완료 / 토큰 API 계약 확인 / 실화면 확인 대기
- 영향 범위: 사용량 조회, 스트리밍 사용량 이벤트, 모아AI 입력 화면

## 어떤 이슈였나

사용자 화면에 `오늘 남은 사용량 %`처럼 숫자가 빠져 표시됐다.

## 원인과 확인 근거

사용량 조회에 TypeScript 타입만 지정하고 실제 JSON 응답을 검사하지 않았다. 화면이 `remaining_percent`를 직접 렌더링하므로 이 필드가 없으면 React가 숫자 부분을 생략하고 `%`만 표시한다. 스트리밍 사용량 이벤트도 검증 없이 상태에 저장했다.

이전 횟수 기준 응답이나 퍼센트 필드가 누락된 토큰 응답으로 같은 문제를 재현했다. 사용자가 접속한 백엔드의 실제 응답은 이번 환경에서 확보하지 못했으므로, 운영 배포 버전 불일치를 확정 원인으로 기록하지 않는다.

## 어떻게 수정했나

- 공통 사용량 파서로 한도·사용·예약 토큰 수와 초기화 날짜를 검증한다.
- 검증된 실제 토큰 수로 잔여량과 퍼센트를 계산해 퍼센트 필드의 누락 또는 잘못된 값에 영향을 받지 않는다. 백엔드와 동일하게 소수점 한 자리로 반올림한다.
- 이전 횟수 기준 응답은 토큰 퍼센트로 임의 변환하지 않는다. 조회 실패 안내와 다시 확인 버튼을 표시하고 질문 보내기를 비활성화한다.
- 호환되지 않는 스트리밍 사용량 이벤트는 상태에 반영하지 않고 정상 답변 수신은 계속한다.
- `pnpm test:ai-usage` 회귀 검사를 만들고 `make test`에 포함했다. 브라우저 QA에도 이전 응답 실패 → 다시 확인 → 퍼센트 필드 없는 토큰 응답 성공 시나리오를 추가했다.

## 검증 결과

- `pnpm test:ai-usage`: 통과. 퍼센트 누락, 실제 토큰 기준 계산, 100%·75%·0%, 초과 사용, 이전 횟수 응답, 잘못된 숫자·날짜, 잘못된 사용량 이벤트 후 정상 답변 완료를 확인했다.
- `pnpm check`: 포맷·린트·타입 검사 통과. 브라우저 QA 수정 후 해당 파일 ESLint도 통과했다.
- `pnpm exec next build --webpack`: 운영 빌드 통과.
- `git diff --check`: 통과.
- 로컬 포트 바인딩이 제한된 현재 환경에서는 브라우저 QA를 실행하지 못했다. 실제 회원의 화면이 정상화됐다는 검증은 아니다.

## 운영 적용과 남은 작업

수정한 프론트를 적용해야 한다. 접속한 백엔드가 아직 `{limit, used, remaining}`을 반환한다면 이전 횟수 기준 API이므로, 토큰 DB migration과 최신 Spring/RAG 적용이 필요하다. 이 경우 프론트 수정만으로 실제 토큰 사용량을 복원할 수 없다. 이번에 운영 DB 적용이나 서비스 배포는 수행하지 않았다.

## 2026-10-14 사용량 확인 실패 후속 조사

앞선 프론트 수정은 숫자 없는 응답을 실패로 처리하도록 바꿨지만, 실제 사용 중인 백엔드를 갱신하지 못했다. 그러므로 `사용량을 확인하지 못했어요`라는 메시지만 반복됐다. 이전의 표시 검사 통과를 실제 서비스 정상화로 판단할 수 없다.

### 확인한 원인

- Chrome의 해당 모아AI 화면은 `localhost:3000`에 접속돼 있다. Network 패널에서 `/api/proxy/me/ai-usage` 요청의 HTTP 200 성공과 화면의 확인 실패 메시지를 함께 확인했다.
- 로컬 프론트는 `http://localhost:8080` 백엔드를 사용한다.
- 관리 PID 기록과 백엔드 기동 로그는 PID 39051이 `/tmp/moadam-local/backend-runtime.jar`로 2026-10-13 16:12에 시작됐음을 보여준다.
- 이 실행 파일의 `AiUsageResponse.class`를 `javap`로 검사하면 `limit()`, `used()`, `remaining()`, `resets_at()`만 있다. 즉, 새 프론트에 필요한 토큰 필드가 없는 이전 횟수 버전이다.
- 최신 `backend/target/community-0.1.0.jar`에는 `limit_tokens()`, `used_tokens()`, `reserved_tokens()`, `remaining_tokens()`, `available_tokens()`, `used_percent()`, `remaining_percent()`, `resets_at()`가 있다.
- 연결된 Moadam Supabase에서 읽기 전용 SQL로 `ai_daily_token_usage`, `ai_token_requests`, `ai_reserve_tokens(uuid,uuid,integer,integer)`, `ai_finish_tokens(uuid,uuid,boolean)`의 존재를 확인했다. 로컬 환경 설정도 같은 Supabase 프로젝트를 가리킨다. 따라서 이번 문제 때문에 SQL Editor에서 추가 SQL을 실행할 필요는 없다.

### 준비한 수정과 검증

최신 소스로 `mvn -o -Dmaven.repo.local=/tmp/community-m2 -DskipTests package`를 실행해 백엔드 실행 파일 빌드를 완료했다. 기존 실행 파일을 사용하는 프로세스의 교체가 필요하다. 표시 로직을 다시 바꾸거나 이전 질문 횟수를 토큰 퍼센트로 환산하는 것으로 해결하지 않는다.

`/tmp/moadam-local/restart-token-backend.mjs`를 준비했다. 관리 PID의 실제 명령이 모아담 로컬 백엔드인지 검사한 다음 SIGTERM으로 정상 종료하고, 최신 jar를 별도 파일로 복사해 재시작한다. `.env`를 메모리에서 읽고 비밀값은 출력하지 않는다. DB migration은 실행하지 않는다. 재시작 후 공개 OpenAPI에서 토큰 사용량 계약을 확인한다.

### 현재 실행 제한과 남은 확인

현재 세션에서 기존 프로세스에 대한 제어는 `Operation not permitted`로 거절됐다. 권한 확장 실행도 자동 승인 정책의 `sandbox_approval: false` 때문에 거절됐다. 따라서 실제 백엔드 교체를 실행하지 못했으며, 화면 정상화를 완료했다고 보고하지 않는다.

로컬 터미널에서 다음 명령으로 준비한 재시작을 실행한 뒤, 모아AI의 `다시 확인`을 눌러 숫자와 `%`가 표시되고 질문 보내기가 활성화되는지 확인해야 한다.

```sh
node /tmp/moadam-local/restart-token-backend.mjs
```

## 2026-10-14 권한 변경 후 전체 재시작

사용자가 권한을 변경하고 프로젝트 전체 재시작을 요청했다. 최신 백엔드 jar를 다시 빌드한 뒤, 관리 PID의 명령이 해당 프로젝트의 프로세스인지 확인하고 백엔드·RAG·프론트를 SIGTERM으로 종료했다. 세 서비스를 최신 소스로 재시작했다.

- 프론트: `http://localhost:3000`, 새 PID 62853.
- 백엔드: `http://localhost:8080`, 새 PID 62852. 최신 jar의 별도 복사본 `backend-token-runtime.jar`를 사용한다.
- RAG: `http://localhost:8000`, 새 PID 62851. 실제 `openai` provider 설정을 유지했다.
- 세 서비스의 HTTP 200 응답과 백엔드 DB readiness를 확인했다.
- 실행 중인 백엔드의 공개 OpenAPI를 다시 읽어 `limit_tokens`, `used_tokens`, `reserved_tokens`, `remaining_tokens`, `available_tokens`, `used_percent`, `remaining_percent`, `resets_at`이 있는 최신 계약을 확인했다.
- 사용량 파서 회귀 검사를 다시 실행해 통과했다.
- `/tmp/moadam-local/start.mjs`도 최신 빌드 파일을 복사해 실행하도록 갱신했다. 다음 기동에서 이전 jar를 다시 사용하는 일을 방지했다. 전체 정상 종료·재시작과 계약 검증은 `/tmp/moadam-local/restart-project.mjs`로 준비했다.

로그인된 Chrome 탭의 화면 확인은 사용자의 다른 탭 조작과 겹쳐 자동화가 중단됐다. 따라서 실제 숫자 표시까지 확인했다고 기록하지 않는다. 구버전 백엔드 실행 문제는 해소했고, SQL 변경과 운영 배포는 수행하지 않았다.
